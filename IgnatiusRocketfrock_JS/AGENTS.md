# INTRO #

This is about a 2D platformer where a catoony wizard as protagonist for a 2D platformer game. 
The game is written in HTML+JS.  
He will usually be running from left to right but we can easily mirror all assets.
He will be animated from a part of assets.

## SOURCE ORGANIZATION RULE ##

Use `ARCHITECTURE.md` as the authoritative module map. Portable gameplay belongs in `src/core/`, engine-neutral cross-layer helpers in `src/shared/`, browser startup/input in `src/browser/`, Canvas and visual runtime code in `src/presentation/`, and editor-only helpers in `src/tools/`. Use lowercase kebab-case and unique descriptive filenames; do not add loose root JavaScript files or several ambiguous files named `app.js`. The future C++ parity commitment applies to `src/core/` and shared runtime data, not to browser, Canvas, or editor implementations. Update tests and all three architecture/planning documents whenever a file moves or changes classification. `src/core/` must import only portable core or shared modules; revision 135 removed the former colour-map boundary violation.

## VIEWPORT SCALING RULE ##

The game uses a shared virtual viewport. On narrow mobile screens the renderer scales the whole canvas down instead of scaling individual sprites or physics values. Keep gameplay, collision, camera, particle, and level coordinates in virtual game coordinates. Convert mouse, touch, and pointer screen coordinates through the viewport transform before passing them into gameplay controls.

## BROWSER STARTUP LOADING RULE ##

`game.html` must display a loading surface before the module script executes. Initial startup loads the level first, then passes `world.atlasManifests` into `createRenderer`; do not restore blind sequential probing of every possible environment atlas. Character projects and independent atlas resources may load concurrently, but progress must remain monotonic and the loading surface must stay visible until JSON, images, collision manifests, colour-map caches, and the first drawable frame are ready. Level transitions must call `renderer.ensureEnvironmentAtlases` before applying atlas collision for a newly referenced level.


## LEVEL COLOUR-MAP RULE ##

Level-wide environment recolouring is stored in `level.colorMap`. Normalization and colour mathematics live in `src/shared/level-color-map-data.js`; browser canvas caching lives in `src/presentation/level-color-map-cache.js`. Preserve the original atlas image and rebuild an offscreen recoloured atlas only when the normalized colour-map cache key changes. Normal render frames must use the cached image through ordinary `drawImage`; never loop over pixels per frame. Apply the map only to environment atlas artwork, not to the cave background, characters, entities, alpha, or collision data.

It must never generate gameplay collision, walkable platforms, navigation supports, or physics geometry. All authoritative floors, walls, ceilings, and platforms remain separately authored in the playing-area layer. The cave opening may occlude actors and use a subtle foreground parallax factor, while outward-facing rock artwork feathers into opaque black to imply a much larger unseen rock mass. Foreground placements automatically disable atlas collision and gameplay attributes, render after actors with the same cave parallax, and use cached brightness/saturation plus a broad eased outward fade that reaches opaque black before the exterior mask takes over. Generated perimeter placements are explicit level records marked `generatedBy: "cavePerimeter"`, so regeneration replaces only generated art and never deletes manually placed foreground objects. Revision 145 adds an editor-only warning for collision-bearing atlas placements that are completely outside the opening by more than a conservative margin; the warning must never mutate authored geometry or turn the cave perimeter into collision. Revision 147 derives a non-editable sampled outset from the authored perimeter and `caveWindow.feather`; the editor displays that outset as the full-black boundary, and runtime explicitly restores opaque black outside the same loop so the guide remains truthful. Revision 211 permits one narrow gameplay use: `src/shared/cave-kill-boundary-data.js` derives a camera-independent lethal player loop from that exact outset, and the core defeats Ignatius only after his complete body is outside it. This threshold must route through the shared death lifecycle and must never become collision, navigation, projectile geometry, an editable second spline, or a Canvas-pixel test. Keep gameplay platforms close enough to the visible opening that their purpose remains legible; geometry far outside the cave window is an authoring error, not hidden level design. The editor may preview the exterior with a flat shade. Runtime uses a reusable offscreen black mask with an outward feather and subtle camera-relative foreground parallax. Perimeter decoration is deterministic for a given spline, seed, maximum spacing, scale, and loaded tagged atlas catalog; generated assets overlap slightly inward across the spline so the playable-side edge remains visible while the outward side hands over to black; horizontal floor/ceiling runs adapt spacing to actual sprite coverage so smaller formations overlap rather than expose gaps. It remains explicit presentation data and never contributes collision. The Level Editor must cull off-screen placements, cache treated foreground frames, suppress generated-object guides unless selected, and avoid serializing the complete level on every drag-frame redraw. Do not move cave-window curve math into `src/core/`.


## WRENCH ROCKET GLOW CACHE RULE ##

Wrench-modified projectile rockets carry their launch-time wrench effect ID and tint in portable projectile state. Presentation generates the matching fuzzy outline once per projectile-frame/tint pair through `src/presentation/rocket-glow-cache.js`, using separable silhouette expansion and blur passes, then reuses the padded offscreen surface through ordinary `drawImage`. Never perform alpha extraction, dilation, blur, tinting, or temporary-canvas creation in the per-frame projectile loop. Draw the cached glow behind the authored rocket and keep standard or Speed Shot-only rockets unmodified.

## CANVAS WORLD-RENDER PERFORMANCE RULE ##

Static environment visuals must be partitioned and sorted only when the `world.visuals` array changes, not rebuilt with `map/filter/sort` every frame. Before any Canvas transform, filter, gradient, or `drawImage`, conservatively reject visuals whose rotated world bounds do not intersect the expanded viewport; cave-foreground culling must include the same parallax offset used for drawing. Apply equivalent conservative rejection to dynamic targets, pickups, enemies, smoke puffs, and projectiles, while including projectile trails in their bounds. Cache darkened/desaturated foreground frame canvases by atlas frame, treatment, and level colour-map key rather than applying `ctx.filter` to every placement every frame. Render the soft cave-window mask on a reduced-resolution reusable surface, reuse it while camera/view/perimeter inputs are unchanged, and upscale only at composition. Keep renderer timing and static/dynamic drawn/culled counters available through the debug panel. If optimized Canvas 2D still misses the target on representative decorated caves, preserve these cached visual lists and bounds as the input model for a later WebGL2 renderer rather than abandoning them.


## EDITOR PANEL ERGONOMICS RULE ##

Character, level, and asset editors must let each right-side inspector panel collapse independently from its heading. Preserve the per-editor collapsed state in local storage, keep the primary heading and accessible expand/collapse button visible, and do not hide or mutate authored data when a panel is collapsed.

## LEVEL PLACEMENT TRANSFORM RULE ##

Level atlas placements may use `mirrorX`, `mirrorY`, and center-based `rotation` in radians. The level editor displays rotation in degrees, but exported/runtime data remains radians. Rendering, editor hit testing, selection outlines, asset guide overlays, and atlas-derived collision must all use `src/shared/level-transform.js`. Never add a separate visual-only rotation or mirror path, because it would desynchronize collision from the art. Right-mouse drag is reserved for panning the level editor regardless of the active placement tool.

## MOVING PLATFORM RULE ##

Moving platforms are ordinary collision-bearing atlas placements with an optional normalized `movement` record. Schema/default ownership belongs in `src/shared/moving-platform-data.js`; deterministic phase changes, collision translation, rider carrying, fade/despawn, and restoration belong in portable core. Store the destination as a relative offset from the placement start so moving the authored object moves its whole route. The safe default is an automatic shuttle that pauses at both endpoints. Every pattern that hides or despawns a platform must restore it automatically after a bounded authored time; never create a level state that can be repaired only by deliberately killing or resetting Ignatius. Hidden/fading platforms must not retain collision, and collision must return only when the platform is fully restored. Update platforms before actors and carry a standing player or living character enemy by exact platform delta through authoritative physical support identity, not friction. Dynamic platform geometry must not be baked as static enemy navigation. Predictable automatic/rider shuttles may add runtime-only endpoint supports, step-only boarding/disembarking, and explicit ride edges; signal and disappearing platforms must stay outside autonomous routes unless later work supplies an explicit availability contract. Crushing and full-black death semantics still require dedicated implementations rather than editor-only assumptions.


## POWER-UP EFFECT RULE ##

Portable effect identity, duration/permanence, stacking or refresh behavior, exclusive effect groups, clear-on-death policy, serialization fields, HUD metadata/priority, randomized pickup pools, and rocket-profile tuning belong in `src/shared/power-up-data.js`. Activation, fixed-step expiry, collection, deterministic session-seeded wrench rolls, sixty-second pickup respawns, projectile spawning, homing, AoE, and Boomerang return/refund belong in `src/core/simulation.js`; Canvas tinting, composite atlas drawing, bobbing, projectile scale, and explosion presentation belong in `src/presentation/canvas-renderer.js`. The persistent top-left Health/Fuel/Power HUD belongs in `game.html` plus `src/browser/game-bootstrap.js`, and it must choose an effect through the shared priority helper rather than browser-only ordering. Do not encode gameplay behavior in icon names or editor visuals. Speed Shot is independent of the mutually exclusive wrench group and has higher HUD priority. Wrench replacement must never cancel Speed Shot, and none of these projectile effects may silently alter backpack boost drain or physics.

## ANIMATION PIPELINE RULE ##

Ground running is data-driven through `assets/ct_anim_wizard_run_1.json` and `src/shared/animation-data.js`. Do not add new run-pose formulas to the renderer or scale animation values per sprite. Animation `x`/`y` values are unscaled rig-space pixels, `rotation` is radians, `scale` multiplies the rig part target height, and `alpha` is scalar opacity. The procedural run and its comparison mode were removed in revision 056. Edit run keyframes in `character-editor.html`; shared keyframe mutations belong in `src/tools/character-editor/animation-editor.js`.

The retained bat in `enemy_005` use still-frame animation without a second runtime or editor pipeline. A frame-swapped character stacks atlas frames as ordinary rig parts, registers them on one stable visual landmark, and uses step-keyed `alpha` tracks so exactly one frame is visible at a time. Preserve the source sequence order unless the user explicitly requests editing it. Keep this data-driven in numbered character/rig/atlas/animation JSON; do not add a dedicated still-frame editor mode unless repeated use justifies it.

## CHARACTER DOPESHEET RULE ##

Puppet Forge's full dopesheet is editor-only. Build its rows through `src/tools/character-editor/dopesheet-data.js` and include only supported rig-part properties with at least two finite authored keyframes. All rows share the animation duration and playhead. Selecting or scrubbing a dopesheet row may change editor selection and preview time, but must not create, delete, merge, or otherwise mutate keys unless the user performs an explicit editing action through the existing keyframe tools. The Cykle animation control remains the animation clip's authoritative `loop` flag, not a separate preview-only preference.

## SHARED ACTOR COLLISION RULE ##

Player and enemy feet use the same foot-position convention and the same swept horizontal/vertical collision queries against solids, collision segments, and collision polygons. Enemy navigation may predict transitions offline, but runtime traversal must still pass through those shared actor collision queries. Do not let NPC drops ignore ordinary ground collision or let baked jump arcs use a narrower body than runtime collision. A destination support on a large polygon only exempts contact while the actor centre is actually over that support; never treat contact with an unrelated wall or ledge on the same polygon as a valid landing. Upward landing candidates may use stable partial body overlap near an edge, because requiring full-body fit at first contact can turn a physically reachable narrow pillar into a late wall-clipping jump. Shared baseline body rectangles, enemy projectile hurtboxes, and melee reach rectangles belong in `src/shared/actor-geometry.js`; debug overlays must call those helpers rather than copying gameplay geometry.

## CHARACTER GROUND CONVENTION ##

Character-local `y = 0` is the authoritative runtime ground/foot line. Puppet Forge must draw this line in Rig and animation mode. Dragging the guide label may reposition the editor view, but must never mutate rig or animation data. Do not rely on per-character runtime ground offsets to repair authored hovering. Normalize a character project offline by applying one uniform rig-space Y translation to rig anchors, setup offsets, animation reference poses, and every Y keyframe, including projectile parts. Keep `rig.global.groundOffset` and `rootYOffsetFromGround` at zero for normalized generic characters.

## ANIMATION-AUTHORED PROJECTILE HANDOFF RULE ##

Projectile sprites may remain rig parts while an attack animation prepares them, but gameplay ownership must be explicit. Store a `projectile` descriptor on the rig part with a stable ID, launch type, animation slot, and authored `releaseTime` in seconds. When a shared rig contains several tagged projectiles, the character definition selects its active one through `projectilePart`. Puppet Forge may show the part's final keyed time as a reference, but the simulation must use the explicit release time. The browser character loader may sample the rig-space release transform and hydrate a plain combat profile; `src/core/simulation.js` owns launch velocity, homing/ballistics, collision, damage, events, and serialization after handoff. The renderer must hide the animation-controlled part at and after release so the simulation projectile is the only visible copy.

## ENEMY PROJECT NAMING RULE ##

Enemy character projects use stable numbered filenames rather than species-specific filenames: `ct_char_enemy_0XX.json`, `ct_rig_enemy_0XX.json`, `ct_atlas_enemy_0XX.json`, `ct_atlas_enemy_0XX.png`, and `ct_anim_enemy_0XX_<slot>.json`. Keep the human-readable species/name in `displayName`, roles, and tags, not in the filenames. `enemy_001` is currently the Skeleton Guard. ## CHARACTER TOOL DIRECT-EDIT RULE ##

Puppet Forge direct transform editing uses the same rig-space animation coordinates as exported JSON. The canvas view zoom is presentation-only. Convert pointer positions through `src/tools/character-editor/character-editor-view.js`; never bake preview zoom, canvas pixels, mirroring, or CSS scale into X/Y/rotation keyframe values. Direct drags must create missing keys at the current playhead before mutation so sampled in-between poses do not masquerade as persistent edits.

Interactive and story props use `assets/it_atlas_001.json` for pixel rectangles and `assets/it_entities_001.json` for editor templates/state-to-visual mappings. Do not hardcode item sprites directly into the Level Editor or renderer. Placed catalog entities copy `visualStates` into level JSON, and entity visuals may use `actorFront` when artwork must be drawn after the player, such as the foreground half of an open portal. Runtime state changes must go through `setWorldEntityState` so the current visuals stay synchronized with entity state. Dedicated `wizard_entry_door` and `wizard_exit_door` entities own level transitions. The entry door replaces `wizardStart`; the exit door replaces the plain `exit` marker and is mirrored by default. Both snap to nearby authored support lines. A doorway entity's `y` is the walkable threshold under the meeting door leaves, not the bottom of its full sprite; preserve `floorAnchorYFactor` in both runtime and editor geometry. Doorway-only wizard scaling is presentation state in `player.renderScale` and must not alter gameplay collision dimensions. Keep transition destination and timing data on the doorway entity, and keep behaviour separate from the visual catalog.

## PLAYER ROCKET TARGET PRIORITY RULE ##

When Ignatius launches a homing rocket, select the closest active enemy target in the half-plane he is facing. Only when no active target exists on that side may the closest target behind him be selected. Distance is measured from the mounted rocket launch point. A rocket already in flight keeps its valid target; this priority is used for launch and replacement after a target becomes inactive.

## PLAYER START AND ARTWORK TARGET RULE ##

Authored `wizardStart` coordinates are foot positions. After atlas collision is built, starts within half a wizard height above a `walkable` or `blockable` line are snapped to that support; keep the runtime and Level Editor implementations behaviorally identical. Portal introductions must use the resolved ground Y before control is released. Atlas-backed target entities should expose a normalized `targetAnchor` inside their entity rectangle and may set `showTargetMarker: false`; do not reintroduce a separate visible homing dot when the artwork already contains a clear bullseye.

Closed blockable atlas loops are solid areas, not only boundary hints. After ordinary axis sweeps, the simulation must depenetrate Ignatius from any overlapping solid rectangle or closed collision polygon along the nearest axis exit. This recovery must also work from a stationary or already-invalid embedded state, and must not change the player's authored collision dimensions.


## REACTIVE WORLD OBJECT RULE ##

Destructible and otherwise gameplay-relevant world props are authoritative `gameState.reactiveObjects`, not renderer effects. Level entities may author health, state names, projectile multipliers, blocking flags, collision-state lists, collision insets, and state-to-visual mappings. Projectile sweeps must resolve the earliest enemy, reactive-object, or terrain impact. When a reactive state changes, update its entity visual through `setWorldEntityState` and rebuild only that object's dynamic solid. Destroyed or inactive objects must not leave invisible player or projectile collision behind. Keep reactive-object transitions, health, collision, events, and serialization in `src/core/`; the renderer only presents world visuals and smoke.

Mailbox letters are entity-authored story data, and a level may contain several mailboxes. Keep trigger distance, durations, atlas frame IDs, editor copy, and Ignatius's thought on each mailbox entity in level JSON. The simulation owns phase progression and input locking; the renderer only draws the active scroll or thought bubble from `state.story.mailboxEvent`. Do not hardcode level-specific prose or trigger coordinates in the renderer.

## Enemy AI and platform navigation

Enemy behaviour flavour belongs in the enemy catalog and level entity, not in visual character-project JSON. Use `strategy: "simple_patrol"`, `"hunter"`, `"sentry"`, or `"bomber"` as the current field. Accept legacy `behavior` and `chaseSpeed` only while importing older data, then normalize them to `strategy` and `runSpeed`; never emit or retain the aliases in current catalog, level, editor, or runtime state. Ignore and discard legacy `awarenessVerticalRange`, because perception is radial plus facing-cone only. Hunter movement capability is authored with `walkSpeed`, `runSpeed`, `jumpHeight`, `jumpGravity`, and `maxFallDistance`. Keep route construction and jump feasibility in `src/core/enemy-navigation.js`, and keep awareness, attack-position selection, traversal, glare, return-home, stranded-patrol, bomber flight, and projectile-release state transitions in portable simulation code. The renderer may visualize route/state diagnostics but must never choose a route or AI transition.

`locomotion: "flying"` is a movement-mode qualifier, not a strategy. Flying character enemies remain portable simulation actors but do not ground-snap, acquire support identities, or enter the hunter navigation graph. Ordinary flying patrols use deterministic horizontal motion with authored vertical bobbing. Bombers use portable eased velocity steering, a curved approach arc, restrained loitering wander, compact terrain probes, and a release-height band around their authored station above Ignatius. They must not drop merely because they cross his horizontal position while still too low. A defeated flying enemy keeps its fly loop, accelerates away from Ignatius, and becomes invisible only after crossing its authored fly-off distance; do not reuse grounded corpse gravity for it. A ground-locomotion character enemy that receives lethal damage while airborne must finish its existing jump or drop through ordinary portable collision, then begin the authored death animation only after landing. Never freeze a death pose in midair and then restart corpse gravity after the clip. The Level Editor must preserve the field and skip automatic ground snapping for flying entities.

A hunter gets one ordinary jump only. Do not reuse Ignatius's double-jump or rocket mechanics. Treat only upward-facing closed-polygon edges as standable supports, keep blocking footprints out of floor supports, and launch vertically overlapping jumps from a body-clear side of the obstacle. For a lower separated support, a downward jump must carry the hunter's full body beyond the source wall before the feet descend below the source surface. A ranged hunter may enter unreachable glare only after both the wizard's support region and every reachable clear firing position have failed. Validate those positions using the projectile's authored origin and launch trajectory. When awareness is lost after engagement, preserve the last genuinely seen player foot position, route to the closest reachable point to it, and only then begin the glare/give-up sequence. Do not steer toward the hidden current player position. If a hunter cannot return to its original support, it should adopt the current reachable support as a temporary patrol and periodically retry the home route. Do not visibly despawn stranded enemies as a navigation shortcut.

The awareness hold keeps an engagement alive and delays glare/give-up; it must not freeze movement. While the target is outside the facing cone, continue any route chosen while the target was visible. If no route is active, immediately begin routing toward the last genuinely seen position even while the hold timer is still running.

A lower floor may overlap the source ledge horizontally, so controlled descent generation must test both physical ledge edges rather than only destinations that lie completely to one side. Prefer an ordinary gravity-driven walk-off when the body can clear the source wall and the fall is within `maxFallDistance`; reserve a downward jump for gaps that actually require launch velocity. During a controlled walk-off, runtime may ignore only the source obstacle for a short, body-bounded departure window. All other geometry remains collidable, and ordinary collision must own the landing. A straight drop through a one-way walkable support must likewise ignore that support until the body is decisively below it.

## Jump run-up guardrail

Do not execute hunter jumps by walking to the wall-side takeoff point, stopping, and assigning an airborne velocity. Non-vertical jump edges must include a clear source-support run-up whenever physical acceleration requires one. Runtime must preserve the committed run-up across ordinary repath intervals, accelerate toward the required launch speed, and enter the airborne phase at the baked takeoff point. Route cost and graph preview should expose the run-up rather than hiding it as an execution detail, and route cost should prefer an obstacle-clear takeoff over an equally feasible nose-to-wall launch. If ordinary full-body collision lands the hunter safely on a neighbouring valid support rather than the nominal target, accept that support and replan instead of counting a navigation failure.

Do not force a low-speed downward jump to back across an entire narrow ledge. Its preferred run-up should be based on acceleration distance plus a modest stability margin; retain the longer body-width run-up for upward obstacle-clearing jumps.

## GAME MENU, SETTINGS, AND ELECTRON RULE ##

Game-facing settings use the versioned schema in `src/shared/game-settings-data.js` and browser persistence in `src/browser/game-settings-store.js`. The default music volume is 10%, effects volume is 80%, difficulty is Normal, and rendering quality is Medium. When loading version-2 settings, migrate only the former exact 60% music default to 10%; preserve every other saved volume. Difficulty currently scales only damage received by Ignatius through the central `damagePlayer` path; it must not silently change enemy speed, health, awareness, or Ignatius's outgoing damage. Explicitly lethal rules may bypass difficulty. Rendering quality currently scales only rocket-trail and explosion particle density, not collision, simulation timing, camera, or authored level data.

The pause menu owns ordinary pause/resume navigation and settings presentation. Opening it must stop fixed-step simulation and closing it must restore the pause state that existed before the menu opened. Losing window focus or hiding the page must open or preserve the pause state and must never resume automatically on focus return. Every paused state must transiently mute music and reduce the effective sound-effects bus volume to zero without overwriting either persisted slider. Keep Escape, direct MENU, and browser fullscreen controls consistent and accessible. The persisted `autoFullscreen` preference is browser policy: active play requests fullscreen from a valid user gesture, while menu/debug pause requests windowed mode. Electron is fullscreen-only, hides this preference, and uses the compact display button as EXIT. Menu and Settings controls must remain fully keyboard navigable without leaking those keystrokes into gameplay. Music is synthesized by the browser-owned director from the shared public-domain tune catalog. Keep AudioContext, oscillator scheduling, autoplay unlocking, transient pause muting, and gain control outside portable simulation; levels may author only a normalized tune ID. The Mountain King lead stays in a low contrabass register and uses a dark fundamental/subharmonic profile rather than a bright upper-octave timbre. Do not package recordings or MIDI files without an explicit asset and licensing decision.

Game-facing overlays share one deep-purple surface family. The loading card, HUD/help/debug panels, tuning pane, pause menu, and Settings must derive their backgrounds, text, borders, and accents from the shared purple variables in `game.html`, rather than carrying a separate brown/earth palette. Keep the main menu card and Settings surfaces solid dark purple; do not restore repeating stripe, noise, timber, or fabric-like CSS textures.

Electron remains a thin browser host. Browser/game modules may detect only the narrow `window.electronWindow` preload contract from `src/browser/electron-window-bridge.js`; they must not import Electron or Node APIs. Keep `contextIsolation` and sandboxing enabled, Node integration disabled, external window creation denied, and desktop-only actions such as Exit to desktop hidden when the preload bridge is absent.


## SIGNAL CHANNEL, INTERACTION, AND INVENTORY RULE ##

Signals are portable named-channel events, not direct object references or browser callbacks. Normalize channel IDs through `src/shared/signal-channel-data.js`. Emitters such as levers and keyholes update their own authoritative entity state and then increment the matching channel revision in `src/core/simulation.js`. Listeners remember the last revision they consumed. Do not make a platform poll a lever's visual state, and do not retrigger listeners every fixed step merely because a channel remains active.

The interaction action is ordinary sampled input and must be ignored by gameplay while browser menus own the keyboard. Proximity tests, key requirements, key consumption, one-shot unlocking, and event emission belong in portable simulation. Key and item ownership belongs in `state.inventory.items`; collected presentation records must disappear only after core marks their pickup state. Editor link lines and missing-emitter warnings are diagnostics only and must never synthesize runtime connections.

Moving-platform segments and polygons must retain `movingPlatformId` in both runtime manifest hydration and Level Editor navigation baking. The navigation builder excludes those dynamic records. Do not simply omit them early in the editor baker, because doing so renumbers later collision polygons and invalidates baked support signatures.

## EXCLUSIVE FRAME-PART ANIMATION RULE ##

Still-frame atlas animation may use ordinary rig parts with `presentation.mode: "exclusive_frame_parts"`. The declared ordered parts must use step alpha tracks and exactly one must be visible throughout the clip. Keep this as shared animation data: do not add character-specific renderer branches, and do not place locomotion, AI, collision, or attack behavior in the clip. Puppet Forge must expose this contract as an active frame-based animation workflow, not as hidden JSON metadata. Managed frame parts have editor-owned alpha tracks; ordinary direct alpha editing must not be allowed to violate exclusivity.

## AUTOMATIC LEVEL GENERATOR OWNERSHIP RULE ##

Keep generator algorithms, normalized settings, implementation registries, named deterministic random streams, validation, and provenance engine-neutral in `src/shared/level-generator-data.js`. Theme choices belong in versioned JSON under `assets/level-generator-themes/`; do not bury theme rules in Level Editor DOM code. A fixed seed and settings must reproduce the same selected candidate, and adding a later generation stage must not perturb unrelated named streams. `level.generation.route` is an abstract authoring/provenance graph, not runtime collision or navigation. Generator stages must materialize ordinary existing level records and mark each generated record with its generation run ownership. Clear, regenerate, and generation undo/redo may mutate only generator-owned state and must preserve manual placements, entities, cave data, and collision. Ice or future palette treatments must use atlas allowlists so environment recolouring cannot silently alter doors, story props, treasure, or power-up icons. Generated traversal distances must be measured from catalogued authored walkable collision edges, never from atlas-frame bounds.
