# INTRO #

This is about a 2D platformer where a catoony wizard as protagonist for a 2D platformer game. 
The game is written in HTML+JS.  
He will usually be running from left to right but we can easily mirror all assets.
He will be animated from a part of assets.

## SOURCE ORGANIZATION RULE ##

Use `ARCHITECTURE.md` as the authoritative module map. Portable gameplay belongs in `src/core/`, engine-neutral cross-layer helpers in `src/shared/`, browser startup/input in `src/browser/`, Canvas and visual runtime code in `src/presentation/`, and editor-only helpers in `src/tools/`. Use lowercase kebab-case and unique descriptive filenames; do not add loose root JavaScript files or several ambiguous files named `app.js`. The future C++ parity commitment applies to `src/core/` and shared runtime data, not to browser, Canvas, or editor implementations. Update tests and all three architecture/planning documents whenever a file moves or changes classification. `src/core/` must import only portable core or shared modules; revision 135 removed the former colour-map boundary violation.

## DOCUMENTATION AND PLAN RULE ##

Whenever implementation work uncovers a bug, stale behavior, or deprecated field/code path, record it explicitly in `PLAN.md`, including whether it was fixed immediately or left for later. Any player-facing, editor-facing, or control change that is described in `GameManual.html` must update the manual in the same revision. Keep revision labels shown by game/editor surfaces synchronized with the packaged revision.

## VIEWPORT SCALING RULE ##

The game uses a shared virtual viewport. On narrow mobile screens the renderer scales the whole canvas down instead of scaling individual sprites or physics values. Revision 230 adds a 1920x1080 fullscreen reference presentation in both ports. Fullscreen uses a uniform crop-to-fill scale, never letterboxing or pillarboxing: 16:9 outputs expose exactly the reference world area, while other aspect ratios crop one logical axis instead of revealing additional world. The backing target remains at the physical display resolution so higher-resolution displays preserve additional texture detail. Windowed presentation retains its variable viewport. Keep gameplay, collision, camera, particle, and level coordinates in virtual game coordinates. Convert mouse, touch, and pointer screen coordinates through the viewport transform before passing them into gameplay controls.

## BROWSER STARTUP LOADING RULE ##

`game.html` must display a loading surface before the module script executes. Initial startup loads the level first, then passes `world.atlasManifests` into `createRenderer`; do not restore blind sequential probing of every possible environment atlas. Character projects and independent atlas resources may load concurrently, but progress must remain monotonic and the loading surface must stay visible until JSON, images, collision manifests, colour-map caches, and the first drawable frame are ready. Level transitions must call `renderer.ensureEnvironmentAtlases` before applying atlas collision for a newly referenced level.


## LEVEL COLOUR-MAP RULE ##

Level-wide environment recolouring is stored in `level.colorMap`. Normalization and colour mathematics live in `src/shared/level-color-map-data.js`; browser canvas caching lives in `src/presentation/level-color-map-cache.js`. Preserve the original atlas image and rebuild an offscreen recoloured atlas only when the normalized colour-map cache key changes. Normal render frames must use the cached image through ordinary `drawImage`; never loop over pixels per frame. Apply the map only to environment atlas artwork, not to the cave background, characters, entities, alpha, or collision data.

## CANVAS WORLD-RENDER PERFORMANCE RULE ##

Static environment visuals must be partitioned, sorted, and placed into stable X buckets only when the `world.visuals` array changes, not rebuilt with `map/filter/sort` or globally scanned every frame. Before any Canvas transform, filter, gradient, or `drawImage`, conservatively reject visuals whose rotated world bounds do not intersect the expanded viewport; cave-foreground culling must include the same parallax offset used for drawing. Apply equivalent conservative rejection to dynamic targets, pickups, enemies, smoke puffs, and projectiles, while including projectile trails in their bounds. Cache darkened/desaturated foreground frame canvases by atlas frame, treatment, and level colour-map key rather than applying `ctx.filter` to every placement every frame. Static alpha-blended atlas visuals that overlap should receive bounded asset-local masked copies, crossfading each upper visual over the central 50% of every transformed overlap. Build the definitions only when `world.visuals` changes, use a spatial broad phase rather than consecutive-record grouping, and let runtime and Level Editor reuse the production renderer cache while original placement and collision records remain authoritative. Never mask moving, entity-bound, explicitly dynamic, or `brightenOnly` visuals; keep layer and On Top draw partitions separate. Render the soft cave-window mask on a reduced-resolution reusable surface, reuse it while camera/view/perimeter inputs are unchanged, and upscale only at composition. Keep renderer timing and static/dynamic drawn/culled counters, including spatially rejected static visuals, available through the debug panel. Core collision hot paths must likewise query camera/actor-local X buckets for static solids, segments, and polygons while retaining moving, reactive, or explicitly dynamic records as live candidates and preserving source-order collision precedence. If optimized Canvas 2D still misses the target on representative decorated caves, preserve these cached visual lists and bounds as the input model for a later WebGL2 renderer rather than abandoning them.

## LEVEL PLACEMENT TRANSFORM RULE ##

Level atlas placements may use `mirrorX`, `mirrorY`, and center-based `rotation` in radians. The level editor displays rotation in degrees, but exported/runtime data remains radians. ## MOVING PLATFORM RULE ##

Moving platforms are ordinary collision-bearing atlas placements with an optional normalized `movement` record. Schema/default ownership belongs in `src/shared/moving-platform-data.js`; deterministic phase changes, collision translation, rider carrying, fade/despawn, and restoration belong in portable core. Store the destination as a relative offset from the placement start so moving the authored object moves its whole route. The safe default is an automatic shuttle that pauses at both endpoints. Every pattern that hides or despawns a platform must restore it automatically after a bounded authored time; never create a level state that can be repaired only by deliberately killing or resetting Ignatius. Hidden/fading platforms must not retain collision, and collision must return only when the platform is fully restored. Update platforms before actors and carry a standing player or living character enemy by exact platform delta through authoritative physical support identity, not friction. Dynamic platform geometry must not be baked as static enemy navigation. Predictable automatic/rider shuttles may add runtime-only endpoint supports, step-only boarding/disembarking, and explicit ride edges; signal and disappearing platforms must stay outside autonomous routes unless later work supplies an explicit availability contract. Crushing and full-black death semantics still require dedicated implementations rather than editor-only assumptions.


## ENEMY SPAWNER RULE ##

Successful arrivals begin alerted and engaged and use procedural core/Canvas teleport effects rather than a new image asset. The Level Editor may show an authoring marker, but it must not leak into runtime world visuals.

## SHARED ACTOR COLLISION RULE ##

Player and enemy feet use the same foot-position convention and the same swept horizontal/vertical collision queries against solids, collision segments, and collision polygons. Grounded Ignatius and grounded walking enemies may automatically step onto a higher support only when the rise is up to one fifth of that actor's collision height; larger rises remain blocking and require an authored jump/navigation transition. Enemy navigation may predict transitions offline, but runtime traversal must still pass through those shared actor collision queries. Do not let NPC drops ignore ordinary ground collision or let baked jump arcs use a narrower body than runtime collision. A destination support on a large polygon only exempts contact while the actor centre is actually over that support; never treat contact with an unrelated wall or ledge on the same polygon as a valid landing. Upward landing candidates may use stable partial body overlap near an edge, because requiring full-body fit at first contact can turn a physically reachable narrow pillar into a late wall-clipping jump. Shared baseline body rectangles, enemy projectile hurtboxes, and melee reach rectangles belong in `src/shared/actor-geometry.js`; debug overlays must call those helpers rather than copying gameplay geometry.

## CHARACTER GROUND CONVENTION ##

Character-local `y = 0` is the authoritative runtime ground/foot line. Puppet Forge must draw this line in Rig and animation mode. Dragging the guide label may reposition the editor view, but must never mutate rig or animation data. Do not rely on per-character runtime ground offsets to repair authored hovering. Normalize a character project offline by applying one uniform rig-space Y translation to rig anchors, setup offsets, animation reference poses, and every Y keyframe, including projectile parts. Keep `rig.global.groundOffset` and `rootYOffsetFromGround` at zero for normalized generic characters.

## CHARACTER SHADOW RULE ##

Character shadows are presentation-only projections of the authoritative physical foot point `actor.x / actor.y`. Never anchor a shadow to `characterArtworkOrigin()` or apply `renderOffsetX / renderOffsetY`; those offsets move artwork only. A shadow targets full opacity while the player is `onGround` or a ground enemy has `airborne === false`, and targets zero opacity while jumping, falling, hovering, or using flying locomotion. Canvas and WebGL must share the same 0.2-second fade and must multiply it by any actor/corpse presentation opacity rather than replacing that opacity.

## PLAYER ROCKET TARGET PRIORITY RULE ##

When Ignatius launches a homing rocket, select the closest active enemy target in the half-plane he is facing. Only when no active target exists on that side may the closest target behind him be selected. Distance is measured from the mounted rocket launch point. A rocket already in flight keeps its valid target; this priority is used for launch and replacement after a target becomes inactive.

## PLAYER ROCKET INITIAL TURN RULE ##

Ignatius's homing rocket starts with a brief launch-turn assist, not a straight-up lock. During the existing 0.32-second launch window, standard homing uses strength 6.95; after that window it must return to the ordinary 4.8 homing strength. The 6.95 value is geometry-calibrated: with Ignatius standing beneath a platform whose surface is exactly one unboosted-jump height above his feet, a rocket aimed toward a same-level distant enemy must only just keep its 15-unit collision radius below that platform. A 6.9 launch strength should still clip it in the regression fixture. Do not increase normal mid-flight homing when adjusting this launch turn.

## PLAYER START AND ARTWORK TARGET RULE ##

A `wizard_entry_door` entity owns the player start, and its authored `y` coordinate is the doorway threshold/foot position. After atlas collision is built, entry doors within half a wizard height of a `walkable` or `blockable` line are snapped to that support; keep the runtime and Level Editor implementations behaviorally identical. Portal introductions must use the resolved ground Y before control is released. Retired root-level start records and `magicPortal`/plain `exit` entities are unsupported and must not be reintroduced. Atlas-backed target entities should expose a normalized `targetAnchor` inside their entity rectangle and may set `showTargetMarker: false`; do not reintroduce a separate visible homing dot when the artwork already contains a clear bullseye.

Closed blockable atlas loops are solid areas, not only boundary hints. After ordinary axis sweeps, the simulation must depenetrate Ignatius from any overlapping solid rectangle or closed collision polygon along the nearest axis exit. This recovery must also work from a stationary or already-invalid embedded state, and must not change the player's authored collision dimensions.


## REACTIVE WORLD OBJECT RULE ##

Destructible and otherwise gameplay-relevant world props are authoritative `gameState.reactiveObjects`, not renderer effects. Level entities may author health, state names, projectile multipliers, blocking flags, collision-state lists, collision insets, and state-to-visual mappings. Projectile sweeps must resolve the earliest enemy, reactive-object, or terrain impact. When a reactive state changes, update its entity visual through `setWorldEntityState` and rebuild only that object's dynamic solid. Destroyed or inactive objects must not leave invisible player or projectile collision behind. Keep reactive-object transitions, health, collision, events, and serialization in `src/core/`; the renderer only presents world visuals and smoke.

## Enemy AI and platform navigation

Enemy attack, hurt, and death WAV references belong in the character project under `sounds.attack`, `sounds.hurt`, and `sounds.death`; both runtimes resolve them from the event character ID. Enemy behaviour flavour belongs in the enemy catalog and level entity, not in visual character-project JSON. Use `strategy: "simple_patrol"`, `"hunter"`, `"sentry"`, or `"bomber"` as the sole behaviour field and `runSpeed` as the sole pursuit-speed field. Retired `behavior`, `chaseSpeed`, and `awarenessVerticalRange` fields are unsupported and must not be normalized, emitted, or retained. Perception is radial plus facing-cone only. Hunter movement capability is authored with `walkSpeed`, `runSpeed`, `jumpHeight`, `jumpGravity`, and `maxFallDistance`. Keep route construction and jump feasibility in `src/core/enemy-navigation.js`, and keep awareness, attack-position selection, traversal, glare, return-home, stranded-patrol, bomber flight, and projectile-release state transitions in portable simulation code. The renderer may visualize route/state diagnostics but must never choose a route or AI transition.

`locomotion: "flying"` is a movement-mode qualifier, not a strategy. Flying character enemies remain portable simulation actors but do not ground-snap, acquire support identities, or enter the hunter navigation graph. Ordinary flying patrols use deterministic horizontal motion with authored vertical bobbing. Bombers use portable eased velocity steering, a curved approach arc, restrained loitering wander, compact terrain probes, and a release-height band around their authored station above Ignatius. They must not drop merely because they cross his horizontal position while still too low. A defeated flying enemy keeps its fly loop, accelerates away from Ignatius, and becomes invisible only after crossing its authored fly-off distance; do not reuse grounded corpse gravity for it. A ground-locomotion character enemy that receives lethal damage while airborne must finish its existing jump or drop through ordinary portable collision, then begin the authored death animation only after landing. Never freeze a death pose in midair and then restart corpse gravity after the clip. The Level Editor must preserve the field and skip automatic ground snapping for flying entities.

A hunter gets one ordinary jump only. Do not reuse Ignatius's double-jump or rocket mechanics. Treat only upward-facing closed-polygon edges as standable supports, keep blocking footprints out of floor supports, and launch vertically overlapping jumps from a body-clear side of the obstacle. For a lower separated support, a downward jump must carry the hunter's full body beyond the source wall before the feet descend below the source surface. A ranged hunter may enter unreachable glare only after both the wizard's support region and every reachable clear firing position have failed. Validate those positions using the projectile's authored origin and launch trajectory. When awareness is lost after engagement, preserve the last genuinely seen player foot position, route to the closest reachable point to it, and only then begin the glare/give-up sequence. Do not steer toward the hidden current player position. If a hunter cannot return to its original support, it should adopt the current reachable support as a temporary patrol and periodically retry the home route. Do not visibly despawn stranded enemies as a navigation shortcut.

The awareness hold keeps an engagement alive and delays glare/give-up; it must not freeze movement. While the target is outside the facing cone, continue any route chosen while the target was visible. If no route is active, immediately begin routing toward the last genuinely seen position even while the hold timer is still running.

A lower floor may overlap the source ledge horizontally, so controlled descent generation must test both physical ledge edges rather than only destinations that lie completely to one side. Prefer an ordinary gravity-driven walk-off when the body can clear the source wall and the fall is within `maxFallDistance`; reserve a downward jump for gaps that actually require launch velocity. During a controlled walk-off, runtime may ignore only the source obstacle for a short, body-bounded departure window. All other geometry remains collidable, and ordinary collision must own the landing. Enemies may leave a green one-way support only through a real ledge walk-off and must never intentionally or accidentally drop through its middle. Ignatius has a separate player-only drop action: Down/S or a downward pointer/touch swipe may temporarily ignore green `walkable` lines while he is standing or falling. That exception must never ignore yellow `blockable` lines, areas, or polygons.

## Jump run-up guardrail

Do not execute hunter jumps by walking to the wall-side takeoff point, stopping, and assigning an airborne velocity. Non-vertical jump edges must include a clear source-support run-up whenever physical acceleration requires one. Runtime must preserve the committed run-up across ordinary repath intervals, accelerate toward the required launch speed, and enter the airborne phase at the baked takeoff point. Route cost and graph preview should expose the run-up rather than hiding it as an execution detail, and route cost should prefer an obstacle-clear takeoff over an equally feasible nose-to-wall launch. If ordinary full-body collision lands the hunter safely on a neighbouring valid support rather than the nominal target, accept that support and replan instead of counting a navigation failure.

Do not force a low-speed downward jump to back across an entire narrow ledge. Its preferred run-up should be based on acceleration distance plus a modest stability margin; retain the longer body-width run-up for upward obstacle-clearing jumps.

## RESOURCE INVENTORY RULE ##

Revision 240 makes `resources/resources.json` the authoritative discovery inventory for environment asset atlases and authored levels. The Asset Tool and Level Editor must enumerate `assetAtlasIds` and `levelIds` from that file in listed order; do not restore numbered probing, stop-at-first-missing behavior, or a 099/020 ceiling. A declared resource is expected to exist, so browser authoring loaders use a bounded retry sequence and report a clear configuration error after retries rather than treating a transient failure as end-of-list. Runtime level loading remains dependency-driven through the requested level and its `atlasRefs`; characters remain catalog-driven through `characters/ct_enemies_001.json`. The resource audit must reject missing, duplicate, malformed, or unlisted atlas/level files. `level_temp.json` remains a generated DevTool exception and must never enter the authored inventory.
