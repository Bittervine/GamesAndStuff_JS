# INTRO #

This is about a 2D platformer where a catoony wizard as protagonist for a 2D platformer game. 
The game is written in HTML+JS.  
He will usually be running from left to right but we can easily mirror all assets.
He will be animated from a part of assets.

## SOURCE ORGANIZATION RULE ##

Use `ARCHITECTURE.md` as the authoritative module map. Portable gameplay belongs in `src/core/`, engine-neutral cross-layer helpers in `src/shared/`, browser startup/input in `src/browser/`, Canvas and visual runtime code in `src/presentation/`, and editor-only helpers in `src/tools/`. Use lowercase kebab-case and unique descriptive filenames; do not add loose root JavaScript files or several ambiguous files named `app.js`. The future C++ parity commitment applies to `src/core/` and shared runtime data, not to browser, Canvas, or editor implementations. Update tests and all three architecture/planning documents whenever a file moves or changes classification. `src/core/` must import only portable core or shared modules; revision 135 removed the former colour-map boundary violation.

## VIEWPORT SCALING RULE ##

The game uses a shared virtual viewport. On narrow mobile screens the renderer scales the whole canvas down instead of scaling individual sprites or physics values. Keep gameplay, collision, camera, particle, and level coordinates in virtual game coordinates. Convert mouse, touch, and pointer screen coordinates through the viewport transform before passing them into gameplay controls.

## BROWSER STARTUP LOADING RULE ##

`game.html` must display a loading surface before the module script executes. Initial startup loads the level first, then passes `world.atlasManifests` into `createRenderer`; do not restore blind sequential probing of every possible environment atlas. Character projects and independent atlas resources may load concurrently, but progress must remain monotonic and the loading surface must stay visible until JSON, images, collision manifests, colour-map caches, and the first drawable frame are ready. Level transitions must call `renderer.ensureEnvironmentAtlases` before applying atlas collision for a newly referenced level.


## LEVEL COLOUR-MAP RULE ##

Level-wide environment recolouring is stored in `level.colorMap`. Normalization and colour mathematics live in `src/shared/level-color-map-data.js`; browser canvas caching lives in `src/presentation/level-color-map-cache.js`. Preserve the original atlas image and rebuild an offscreen recoloured atlas only when the normalized colour-map cache key changes. Normal render frames must use the cached image through ordinary `drawImage`; never loop over pixels per frame. Apply the map only to environment atlas artwork, not to the cave background, characters, entities, alpha, or collision data.


## CAVE WINDOW AND FOREGROUND RULE ##

The `level.caveWindow` perimeter is a presentation-only foreground mask and decoration layer. Revision 136 authors its closed smooth/corner spline through `src/shared/cave-window-data.js`; revision 137 renders it through `src/presentation/cave-window-mask.js`; revision 138 adds deterministic tagged-asset generation through `src/shared/cave-window-decoration.js` plus manual `caveForeground` placement; revision 140 adds adaptive overlap, cached outward-to-black sprite treatment, editor culling, and a non-destructive generated-art visibility toggle; revision 141 raises foreground parallax, moves generated art farther into the opening, broadens the eased black handover, and clamps smooth spline handles so wide starter perimeters cannot form corner loops; revision 142 restores the generated-asset scale default to 2× and creates the starter loop just outside the technical world bounds with a consistent margin. It must never generate gameplay collision, walkable platforms, navigation supports, hazards, or physics geometry. All authoritative floors, walls, ceilings, and platforms remain separately authored in the playing-area layer. The cave opening may occlude actors and use a subtle foreground parallax factor, while outward-facing rock artwork feathers into opaque black to imply a much larger unseen rock mass. Foreground placements automatically disable atlas collision and gameplay attributes, render after actors with the same cave parallax, and use cached brightness/saturation plus a broad eased outward fade that reaches opaque black before the exterior mask takes over. Generated perimeter placements are explicit level records marked `generatedBy: "cavePerimeter"`, so regeneration replaces only generated art and never deletes manually placed foreground objects. Keep gameplay platforms close enough to the visible opening that their purpose remains legible; geometry far outside the cave window is an authoring error, not hidden level design. The editor may preview the exterior with a flat shade. Runtime uses a reusable offscreen black mask with an outward feather and subtle camera-relative foreground parallax. Perimeter decoration is deterministic for a given spline, seed, maximum spacing, scale, and loaded tagged atlas catalog; generated assets overlap slightly inward across the spline so the playable-side edge remains visible while the outward side hands over to black; horizontal floor/ceiling runs adapt spacing to actual sprite coverage so smaller formations overlap rather than expose gaps. It remains explicit presentation data and never contributes collision. The Level Editor must cull off-screen placements, cache treated foreground frames, suppress generated-object guides unless selected, and avoid serializing the complete level on every drag-frame redraw. Do not move cave-window curve math into `src/core/`.

## CANVAS WORLD-RENDER PERFORMANCE RULE ##

Static environment visuals must be partitioned and sorted only when the `world.visuals` array changes, not rebuilt with `map/filter/sort` every frame. Before any Canvas transform, filter, gradient, or `drawImage`, conservatively reject visuals whose rotated world bounds do not intersect the expanded viewport; cave-foreground culling must include the same parallax offset used for drawing. Apply equivalent conservative rejection to dynamic targets, pickups, enemies, smoke puffs, and projectiles, while including projectile trails in their bounds. Cache darkened/desaturated foreground frame canvases by atlas frame, treatment, and level colour-map key rather than applying `ctx.filter` to every placement every frame. Render the soft cave-window mask on a reduced-resolution reusable surface, reuse it while camera/view/perimeter inputs are unchanged, and upscale only at composition. Keep renderer timing and static/dynamic drawn/culled counters available through the debug panel. If optimized Canvas 2D still misses the target on representative decorated caves, preserve these cached visual lists and bounds as the input model for a later WebGL2 renderer rather than abandoning them.


## EDITOR PANEL ERGONOMICS RULE ##

Character, level, and asset editors must let each right-side inspector panel collapse independently from its heading. Preserve the per-editor collapsed state in local storage, keep the primary heading and accessible expand/collapse button visible, and do not hide or mutate authored data when a panel is collapsed.

## LEVEL PLACEMENT TRANSFORM RULE ##

Level atlas placements may use `mirrorX`, `mirrorY`, and center-based `rotation` in radians. The level editor displays rotation in degrees, but exported/runtime data remains radians. Rendering, editor hit testing, selection outlines, asset guide overlays, and atlas-derived collision must all use `src/shared/level-transform.js`. Never add a separate visual-only rotation or mirror path, because it would desynchronize collision from the art. Right-mouse drag is reserved for panning the level editor regardless of the active placement tool.

## ANIMATION PIPELINE RULE ##

Ground running is data-driven through `assets/ct_anim_wizard_run_1.json` and `src/shared/animation-data.js`. Do not add new run-pose formulas to the renderer or scale animation values per sprite. Animation `x`/`y` values are unscaled rig-space pixels, `rotation` is radians, `scale` multiplies the rig part target height, and `alpha` is scalar opacity. The procedural run and its comparison mode were removed in revision 056. Edit run keyframes in `character-editor.html`; shared keyframe mutations belong in `src/tools/character-editor/animation-editor.js`.

## SHARED ACTOR COLLISION RULE ##

Player and enemy feet use the same foot-position convention and the same swept horizontal/vertical collision queries against solids, collision segments, and collision polygons. Enemy navigation may predict transitions offline, but runtime traversal must still pass through those shared actor collision queries. Do not let NPC drops ignore ordinary ground collision or let baked jump arcs use a narrower body than runtime collision. A destination support on a large polygon only exempts contact while the actor centre is actually over that support; never treat contact with an unrelated wall or ledge on the same polygon as a valid landing. Upward landing candidates may use stable partial body overlap near an edge, because requiring full-body fit at first contact can turn a physically reachable narrow pillar into a late wall-clipping jump. Shared baseline body rectangles, enemy projectile hurtboxes, and melee reach rectangles belong in `src/shared/actor-geometry.js`; debug overlays must call those helpers rather than copying gameplay geometry.

## CHARACTER GROUND CONVENTION ##

Character-local `y = 0` is the authoritative runtime ground/foot line. Puppet Forge must draw this line in Rig and animation mode. Dragging the guide label may reposition the editor view, but must never mutate rig or animation data. Do not rely on per-character runtime ground offsets to repair authored hovering. Normalize a character project offline by applying one uniform rig-space Y translation to rig anchors, setup offsets, animation reference poses, and every Y keyframe, including projectile parts. Keep `rig.global.groundOffset` and `rootYOffsetFromGround` at zero for normalized generic characters.

## CHARACTER TOOL DATA-LAYER RULE ##

Do not merge atlas-frame rectangles with rig-part semantics. The atlas manifest identifies reusable pixel rectangles in a PNG. The rig assigns those frames to parts and owns pivots, anchors, draw order, roles, and gameplay/editor tags. Character definitions select a rig but must not replace rig parts or pivots; a variant that needs different rig geometry owns a dedicated numbered rig file. Character project selection, blank-template creation, URL loading, and local PNG/JSON workspaces are centralized through `character-editor.html` and `src/tools/character-editor/character-project.js`; do not reintroduce wizard-only hardcoded paths. Atlas rectangle authoring and independent per-document dirty tracking were added in revision 061. Revision 063 added known-project switching for the first enemy plus atlas-frame-to-rig creation with animation synchronization. Revision 064 added its walk clip and records held-equipment grip metadata on the rig; the current clips still author absolute equipment transforms at the animated hand positions. Revision 065 added selected-part **To Back** and **To Front** draw-order controls. Revision 084 added validated clip-metadata editing and in-memory animation duplication that also updates the character animation map; keep shared metadata and duplication mutations in `src/tools/character-editor/animation-editor.js` and stable slot/filename rules in `src/tools/character-editor/character-project.js`. Revision 085 added `src/presentation/character-runtime.js`; all non-tool game loading, arbitrary-rig normalization, animation-slot sampling, and ordered character draw-command creation belong there. `src/presentation/canvas-renderer.js` may select presentation states and execute those commands, but monster behaviour must remain simulation-owned. Revision 093 added an explicit enemy catalog, Level Editor placement/preview, ground snapping, and simulation-owned guard/patrol behaviour for `enemy_001`. Revision 094 added simulation-owned enemy health, swept projectile collision that respects nearer terrain, hurt/death transitions, target deactivation, hit flash, and temporary health-bar feedback. Revision 096 added simulation-owned melee damage, terrain-shielded strike checks, player invulnerability, knockback, and damaging/killable collision surfaces. Revision 097 added patrol-area awareness, faster pursuit, attack lunges, and rapid chained attacks; keep those combat decisions in the simulation while the renderer only presents authored animation slots and feedback timers.


## ANIMATION-AUTHORED PROJECTILE HANDOFF RULE ##

Projectile sprites may remain rig parts while an attack animation prepares them, but gameplay ownership must be explicit. Store a `projectile` descriptor on the rig part with a stable ID, launch type, animation slot, and authored `releaseTime` in seconds. When a shared rig contains several tagged projectiles, the character definition selects its active one through `projectilePart`. Puppet Forge may show the part's final keyed time as a reference, but the simulation must use the explicit release time. The browser character loader may sample the rig-space release transform and hydrate a plain combat profile; `src/core/simulation.js` owns launch velocity, homing/ballistics, collision, damage, events, and serialization after handoff. The renderer must hide the animation-controlled part at and after release so the simulation projectile is the only visible copy.

## ENEMY PROJECT NAMING RULE ##

Enemy character projects use stable numbered filenames rather than species-specific filenames: `ct_char_enemy_0XX.json`, `ct_rig_enemy_0XX.json`, `ct_atlas_enemy_0XX.json`, `ct_atlas_enemy_0XX.png`, and `ct_anim_enemy_0XX_<slot>.json`. Keep the human-readable species/name in `displayName`, roles, and tags, not in the filenames. `enemy_001` is currently the Skeleton Guard. Future automatic discovery should use a generated/indexed enemy catalog or numbered probing; browser code must not pretend it can enumerate an arbitrary static asset directory.

## CHARACTER TOOL DIRECT-EDIT RULE ##

Puppet Forge direct transform editing uses the same rig-space animation coordinates as exported JSON. The canvas view zoom is presentation-only. Convert pointer positions through `src/tools/character-editor/character-editor-view.js`; never bake preview zoom, canvas pixels, mirroring, or CSS scale into X/Y/rotation keyframe values. Direct drags must create missing keys at the current playhead before mutation so sampled in-between poses do not masquerade as persistent edits.

Interactive and story props use `assets/it_atlas_001.json` for pixel rectangles and `assets/it_entities_001.json` for editor templates/state-to-visual mappings. Do not hardcode item sprites directly into the Level Editor or renderer. Placed catalog entities copy `visualStates` into level JSON, and entity visuals may use `actorFront` when artwork must be drawn after the player, such as the foreground half of an open portal. Runtime state changes must go through `setWorldEntityState` so the current visuals stay synchronized with entity state. Dedicated `wizard_entry_door` and `wizard_exit_door` entities own level transitions. The entry door replaces `wizardStart`; the exit door replaces the plain `exit` marker and is mirrored by default. Both snap to nearby authored support lines. A doorway entity's `y` is the walkable threshold under the meeting door leaves, not the bottom of its full sprite; preserve `floorAnchorYFactor` in both runtime and editor geometry. Doorway-only wizard scaling is presentation state in `player.renderScale` and must not alter gameplay collision dimensions. Keep transition destination and timing data on the doorway entity, and keep behaviour separate from the visual catalog.

## PLAYER ROCKET TARGET PRIORITY RULE ##

When Ignatius launches a homing rocket, select the closest active enemy target in the half-plane he is facing. Only when no active target exists on that side may the closest target behind him be selected. Distance is measured from the mounted rocket launch point. A rocket already in flight keeps its valid target; this priority is used for launch and replacement after a target becomes inactive.

## PLAYER START AND ARTWORK TARGET RULE ##

Authored `wizardStart` coordinates are foot positions. After atlas collision is built, starts within half a wizard height above a `walkable` or `blockable` line are snapped to that support; keep the runtime and Level Editor implementations behaviorally identical. Portal introductions must use the resolved ground Y before control is released. Atlas-backed target entities should expose a normalized `targetAnchor` inside their entity rectangle and may set `showTargetMarker: false`; do not reintroduce a separate visible homing dot when the artwork already contains a clear bullseye.

Closed blockable atlas loops are solid areas, not only boundary hints. After ordinary axis sweeps, the simulation must depenetrate Ignatius from any overlapping solid rectangle or closed collision polygon along the nearest axis exit. This recovery must also work from a stationary or already-invalid embedded state, and must not change the player's authored collision dimensions.


## REACTIVE WORLD OBJECT RULE ##

Destructible and otherwise gameplay-relevant world props are authoritative `gameState.reactiveObjects`, not renderer effects. Level entities may author health, state names, projectile multipliers, blocking flags, collision-state lists, collision insets, and state-to-visual mappings. Projectile sweeps must resolve the earliest enemy, reactive-object, or terrain impact. When a reactive state changes, update its entity visual through `setWorldEntityState` and rebuild only that object's dynamic solid. Destroyed or inactive objects must not leave invisible player or projectile collision behind. Keep reactive-object transitions, health, collision, events, and serialization in `src/core/`; the renderer only presents world visuals and smoke.

## Mailbox story guardrail

Mailbox letters are entity-authored story data, and a level may contain several mailboxes. Keep trigger distance, durations, atlas frame IDs, editor copy, and Ignatius's thought on each mailbox entity in level JSON. The simulation owns phase progression and input locking; the renderer only draws the active scroll or thought bubble from `state.story.mailboxEvent`. Do not hardcode level-specific prose or trigger coordinates in the renderer.

## Enemy AI and platform navigation

Enemy behaviour flavour belongs in the enemy catalog and level entity, not in visual character-project JSON. Use `strategy: "simple_patrol"`, `"hunter"`, or `"sentry"` as the only current field. Accept legacy `behavior` and `chaseSpeed` only while importing older data, then normalize them to `strategy` and `runSpeed`; never emit or retain the aliases in current catalog, level, editor, or runtime state. Ignore and discard legacy `awarenessVerticalRange`, because perception is radial plus facing-cone only. Hunter movement capability is authored with `walkSpeed`, `runSpeed`, `jumpHeight`, `jumpGravity`, and `maxFallDistance`. Keep route construction and jump feasibility in `src/core/enemy-navigation.js`, and keep awareness, attack-position selection, traversal, glare, return-home, and stranded-patrol state transitions in portable simulation code. The renderer may visualize route/state diagnostics but must never choose a route or AI transition.

A hunter gets one ordinary jump only. Do not reuse Ignatius's double-jump or rocket mechanics. Treat only upward-facing closed-polygon edges as standable supports, keep blocking footprints out of floor supports, and launch vertically overlapping jumps from a body-clear side of the obstacle. For a lower separated support, a downward jump must carry the hunter's full body beyond the source wall before the feet descend below the source surface. A ranged hunter may enter unreachable glare only after both the wizard's support region and every reachable clear firing position have failed. Validate those positions using the projectile's authored origin and launch trajectory. When awareness is lost after engagement, preserve the last genuinely seen player foot position, route to the closest reachable point to it, and only then begin the glare/give-up sequence. Do not steer toward the hidden current player position. If a hunter cannot return to its original support, it should adopt the current reachable support as a temporary patrol and periodically retry the home route. Do not visibly despawn stranded enemies as a navigation shortcut.

The awareness hold keeps an engagement alive and delays glare/give-up; it must not freeze movement. While the target is outside the facing cone, continue any route chosen while the target was visible. If no route is active, immediately begin routing toward the last genuinely seen position even while the hold timer is still running.

A lower floor may overlap the source ledge horizontally, so controlled descent generation must test both physical ledge edges rather than only destinations that lie completely to one side. Prefer an ordinary gravity-driven walk-off when the body can clear the source wall and the fall is within `maxFallDistance`; reserve a downward jump for gaps that actually require launch velocity. During a controlled walk-off, runtime may ignore only the source obstacle for a short, body-bounded departure window. All other geometry remains collidable, and ordinary collision must own the landing. A straight drop through a one-way walkable support must likewise ignore that support until the body is decisively below it.

## Jump run-up guardrail

Do not execute hunter jumps by walking to the wall-side takeoff point, stopping, and assigning an airborne velocity. Non-vertical jump edges must include a clear source-support run-up whenever physical acceleration requires one. Runtime must preserve the committed run-up across ordinary repath intervals, accelerate toward the required launch speed, and enter the airborne phase at the baked takeoff point. Route cost and graph preview should expose the run-up rather than hiding it as an execution detail, and route cost should prefer an obstacle-clear takeoff over an equally feasible nose-to-wall launch. If ordinary full-body collision lands the hunter safely on a neighbouring valid support rather than the nominal target, accept that support and replan instead of counting a navigation failure.

Do not force a low-speed downward jump to back across an entire narrow ledge. Its preferred run-up should be based on acceleration distance plus a modest stability margin; retain the longer body-width run-up for upward obstacle-clearing jumps.
